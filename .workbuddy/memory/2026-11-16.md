## 违规模块重构：数据不落库（按用户方案实施）
- 新架构：定时任务（10分钟）拉近30天 → 按店铺写 Redis（`dy:violation:{store_pk}`，TTL 20分钟）；查询近30天内任意范围（今天/7天/30天/自定义）读 Redis，状态最多滞后一个周期。超出30天 → 实时拉取，结果放进程内存（`_LIVE` 槽，15分钟TTL，最多8个范围），不进 Redis 不入库；首次查询自动触发后台拉取并返回 `pulling=true`，前端 followRunning 等进度后自动重查。失败后 120 秒内不自动重拉（guard），任务运行中则继续跟随进度。
- 服务层重写：`query_violations`（替代 list_violations）、`options` 同源计算（去掉 statuses）、`_pull_one`/`_refresh_all` 不再写库、`_upsert_rows`/`_query_violations`/`type_value_map` 删除；`dy_violation` 表保留但不再写入（store_service 删店清理逻辑保留）。
- 处罚到期日：最终版为**独立一列「处罚到期时间」**。到期日/筛选均由**后端**负责（用户要求）：service `_due_date`（正则取最大天数+违规时间）写入展示行 `due_date` 字段，`_apply_filters`/router 支持 `due=active|passed`（未到期/已到期，无天数记录不算进任何一边）；schema ViolationRow 加 due_date。前端只负责显示标色：<今天=绿（已结束）、≥今天=红（生效中）（颜色对调过一次，最终以此为准）。到期下拉变化触发 query(false) 显示转圈（.vio-spinner）等待提示。列宽：shop 8 / time 9.5 / id 11 / type 13 / penalty 18.5 / due 10.5 / desc 21 / status 8.5。
- 状态下拉：前端 paint() 按当前结果动态生成（页面有什么就有什么），后端 options 不再返回 statuses。

## 处置状态"已撤销"vs 原站"处置已解除"（已修复）
- 原因：原站"处置状态"列读 `status_text_detail.top_exec_desc_list` 的执行分组，不是 `main_status_text`。实测映射：已处置(1)→已处置、已撤销(2)→已撤销、已解除(3)→处置已解除。违规单撤销但处置已执行完的工单，main="已撤销" 而原站显示"处置已解除"。
- 修复：dy_violation.py 新增 `_display_status`，exec 分组唯一时按分组显示（"已解除"加"处置"前缀），混合分组或无分组退回 main_status_text。下次拉取即生效。
- 遗留：原站"已申诉"状态的字段来源仍未确认（上午的案子），遇到再抓包。
